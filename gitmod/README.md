# gitmod

`gitmod` 是一个轻量的 go.mod 模块版本管理命令行工具。普通命令修改当前目录 `go.mod` 中指定模块的版本号；`god` 子命令通过临时 worktree 批量更新多个分支并提交、推送。不执行 `go get`、`go mod tidy`，也不改动 `go.sum`。

## 特性

- **交互式选择**：直接运行 `gitmod`，通过方向键选择模块，空格或回车按配置的默认版本更新
- **保留注释和格式**：直接在原始字节上做精确替换，`go.mod` 中的注释、空行、对齐格式原样保留
- **支持 replace**：存在带版本的 `replace` 时读取并修改右侧版本，否则修改 `require` 版本；本地目录替换自动跳过
- **支持分支名**：版本参数可以是语义化版本，也可以是任意分支名（如 `master`、`test`），按原样写入 `go.mod`
- **原子写入**：通过临时文件 + 重命名落盘，写入前检测 `go.mod` 是否被并发修改，避免覆盖他人改动
- **主目录兜底**：当前目录没有 `mod.yml` 时，自动回退读取用户主目录下的 `mod.yml`，多项目共享一份配置
- **彩色输出**：终端下区分「更新 / 不变」状态，自动遵循 `NO_COLOR` 与 `TERM=dumb`
- **跨平台对齐**：表格输出按终端显示宽度计算列宽，中文与全角字符不会导致错位
- **跨分支更新**：`god` 先拉取全部目标分支，全部准备成功后再逐个修改模块、以 `-` 提交并推送；工作通过临时 worktree 完成

## 构建

需要 Go 1.17 及以上。使用目录内的 `go.mod` 和 `go.sum` 管理构建依赖，`build.mod` 不会被普通 `go build` 自动读取。

```powershell
cd gitmod
$env:GO111MODULE = 'on'
go build .
```

生成 `gitmod.exe`。如果环境配置了 `GO111MODULE=off`，必须先在当前终端启用模块模式，否则 Go 会到 GOPATH 中查找依赖。

也可以在此目录执行 `./build.ps1`，脚本会在构建期间启用模块模式，完成后恢复原环境设置。首次构建需要依赖缓存或可访问的依赖源，依赖均为公开模块。需要本地离线依赖时，可在模块模式下执行 `go mod vendor`；生成的 `vendor` 目录不纳入版本管理。

## 配置

工具通过 `mod.yml` 知道每个模块简写对应的模块路径和默认版本。默认优先读取当前工作目录下的 `mod.yml`，不存在时回退读取用户主目录下的 `mod.yml`；可通过环境变量 `MOD_CONFIG` 指定配置路径，`--config` 参数优先级最高（须放在命令之前）。

```yaml
modules:
  rpc: [wesure.com/rpcproto, test]
  common: [health/common, test]
  app-insure: [config/app-insure, master]
```

- 键为**简写**，不能是纯数字，也不能是 `list`、`all`、`help`、`god` 等保留字
- 值为 `[模块路径, 默认版本]` 两个元素
- 同一模块路径不允许重复配置

## 用法

```text
gitmod [--config 路径]                 方向键选择，空格或回车按默认版本更新
gitmod [--config 路径] <简写或序号> [版本或分支]
gitmod [--config 路径] list
gitmod [--config 路径] all
gitmod [--config 路径] [--remote origin] god <简写或序号> <分支> [其他分支...]
```

### 交互模式

在项目目录下直接运行：

```sh
gitmod
```

会列出当前项目匹配的模块，用 `↓` / `j` / `Ctrl+N` 选择下一项，`↑` / `k` 选择上一项，支持首尾循环：最后一项向下回到第一项，第一项向上跳到最后一项。空格或回车按默认版本更新，`Esc` / `Ctrl+C` 取消。

### 按简写更新

```sh
gitmod rpc              # 将 rpc 对应模块更新为默认版本 test
gitmod rpc v1.2.3       # 更新为指定版本
gitmod app-insure master # 更新为指定分支
```

### 按序号更新

先运行 `gitmod list` 查看序号，再按序号操作：

```sh
gitmod list
gitmod 1                # 将序号 1 对应的模块更新为默认版本
gitmod 1 master
```

序号从 1 开始，对应当前项目 `list` 的顺序；修改配置顺序或项目依赖后，序号可能变化，请重新查看。

### 批量更新

```sh
gitmod all              # 所有配置项均按各自默认版本更新
```

### 查看列表

```sh
gitmod list
```

输出示例：

```text
序号  简写         模块                   默认版本  当前版本
1    rpc         wesure.com/rpcproto    test     v0.0.0-20260924090412-c0ff38d59431
2    common      health/common          test     v0.0.0-20260509061412-81733ec9d908
```

### 跨分支更新、提交和推送

```powershell
gitmod god 1 a b c
gitmod god rpc a b c
gitmod --config C:/Users/me/mod.yml --remote upstream god 1 a b c
```

将指定模块更新为配置中的默认版本，目标分支为 `a`、`b`、`c`。远端默认是 `origin`，`--config` 和 `--remote` 必须放在 `god` 之前。

配置只从命令启动目录读取一次，沿用 `--config`、`MOD_CONFIG`、当前目录 `mod.yml`、用户主目录 `mod.yml` 的优先级。数字序号按启动目录的 `gitmod list` 解析为固定模块路径，所有目标分支都更新这个模块，不会因不同分支的列表顺序不同而改错模块。也可以直接使用模块简写。

执行分为三个阶段：

1. **全部分支准备。** 从实际推送地址获取所有目标分支，分别创建 detached worktree。存在本地同名分支时，以该分支已提交的版本为起点；否则以远端版本为起点。逐个执行 `pull --ff-only --no-rebase`，然后检查所有分支对应的 `go.mod` 并计算更新内容。任何分支拉取失败、与远端分叉、文件不存在、模块不存在或不可更新，都会停止整个操作，不修改模块、不提交、不推送。此阶段只更新临时 worktree，不修改本地分支引用。
2. **逐个修改并推送。** 全部分支准备成功后，按参数顺序更新模块。仅提交对应的 `go.mod`，提交信息固定为一个 `-`，随后立即推送该分支。版本已经一致时不创建空提交，但仍会推送已更新的分支。存在本地未推送提交且能够正常快进拉取时，这些已提交的变更也会随分支一起推送。
3. **同步本地分支。** 推送阶段结束后，统一将已成功推送的目标分支快进更新到本次推送的版本。本地不存在的同名分支会自动创建。某个分支同步失败时，继续同步其他已推送的分支，最后汇总结果并返回失败状态。

在仓库子目录运行时，每个分支都使用相同相对目录下的 `go.mod`。该文件必须已由 Git 跟踪；符号链接文件及指向临时 worktree 之外的路径不支持批量更新。

不会切换当前目录或其他已有 worktree 的分支。目标分支已在某个工作区检出且需要更新时，工作区干净才执行快进同步，同时更新该工作区文件；存在未提交修改时保留现场，报告本地同步失败并提示处理后手动拉取。未被占用的分支通过临时 worktree 同步。同步不会强制覆盖本地分支，也不会自动暂存未提交修改。

提交或推送失败会停止后续目标，已经推送成功的分支不会回滚。远端在准备阶段之后又有并发更新时，普通推送仍可能被拒绝；工具不会强制推送。输出会列出已成功推送的分支；推送失败时会显示本次提交的哈希，便于后续恢复。

正常完成、失败或可处理的 Ctrl+C 都会清理本次创建的临时 worktree、目录和引用。强制终止进程或系统断电可能阻止清理；清理失败会报告具体路径。

## 行为细节

- 普通命令只读取当前目录的 `go.mod`，`god` 使用各分支对应目录下的 `go.mod`；均按模块路径精确匹配
- 带旧版本的 `replace` 规则仅在 `require` 版本匹配时生效
- 零版本 `v0.0.0-00010101000000-000000000000` 始终跳过
- 版本已与目标一致时输出「不变」，不做写入
- 写入前若 `go.mod` 发生变化，会取消本次写入并提示重试
